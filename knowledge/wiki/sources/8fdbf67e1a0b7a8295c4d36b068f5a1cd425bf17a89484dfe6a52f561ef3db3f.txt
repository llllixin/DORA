# Agent 学习与规划

Agent 是这个项目接下来的重点。项目已有只读有限循环，并在 2026-09-23 完成普通混合 RAG 的知识、索引、检索、引用回答和固定评价；真实 Agent 模型适配器与前端入口仍是下一阶段。
本文核对日期为 2026-09-23。它是学习与设计说明，任务状态统一在 [持续优化路线](../持续优化路线.md)。
面向求职复习的六角度技术讲解、逐层追问和直接回答见 [AI Agent 岗位面试技术说明](AI-Agent岗位面试技术说明.md)。
模型、缓存、工具安全和评估的实际问题集中在 [Agent 问题与经验](问题与经验.md)。
普通 RAG 的数据、架构、分阶段任务与验收标准见 [RAG 整体搭建计划](RAG整体搭建计划.md)。

## 1 先分清四个概念

**LLM 调用**：把问题或事实发给模型，收到文本或 JSON。一次调用可以解释数据，但不会自动替你执行函数。

**工具调用**：模型返回工具名称和参数，程序校验后执行，再把真实结果交回模型。模型提出调用请求，程序拥有执行权。

**工作流**：步骤由代码预先安排。例如“读引擎 → 查证据 → 查知识 → 拼答案”，即使包含 LLM，也可以是固定工作流。

**Agent 循环**：模型在允许范围内决定下一步调用什么，观察结果后继续或结束。它需要停止条件、错误处理和可观察的运行记录。
这些术语存在不同用法，本文采用 [Anthropic 对工作流与 Agent 的区分](https://www.anthropic.com/engineering/building-effective-agents)。

**RAG** 是先检索资料，再把相关内容作为生成答案的上下文；不等于“必须有独立向量数据库”。
本项目现在用关键词与确定性向量混合召回，资料量增大后再按测得的延迟迁移存储。
参考 [RAG 原始论文](https://arxiv.org/abs/2005.11401)。

## 2 现有代码可以复用什么

### 已有 LLM 解释调用

[reasoning/llm.py](../../backend/app/reasoning/llm.py) 的 `LLMProvider.explain` 会调用配置的模型接口，
让模型改写因素名称和建议，再通过 `_merge_with_numeric_stability` 保留/校验部分数值。
这是解释增强，不是工具选择循环。实际是否联网、使用哪个模型取决于环境配置；本次没有调用真实模型验证。
因此旧文档“项目没有 LLM 调用、数据不会出内网”的描述不正确。

### 已有可以包装成工具的业务函数

[routers.py](../../backend/app/routers.py) 提供：

- `query_metric`：读取指标行，对应 `/api/tools/query_metric`。
- `knowledge_search`：词法检索历史知识，对应 `/api/knowledge/search`。
- 引擎与证据查询入口：取得当前规则结论与数据依据。

HTTP 接口存在，只表示程序可以调用。还需要工具描述、参数 schema、允许列表、执行器及结果回传，模型才能使用这些能力。
同一个后端进程可以包装业务函数，不必为了工具调用额外绕一圈 HTTP。

### 已有普通 RAG 与运行记录

[rag/](../../backend/app/rag) 已实现受审核语料导入、版本保留、确定性分块、关键词与向量混合检索、低相关拒答、实时事实分流、引用校验和固定评价。2026-10-14 的 A01 补齐本体类型/方向/来源约束、发布 hash、别名歧义与正确物理维度；当前问题仍只返回 tool_required 提示，实际统一工具执行由后续 A07 实现。词典与评价版本说明见 [知识源](../../knowledge/README.md)。
默认模板回答和哈希 embedding 让门禁可离线复现；可选 OpenAI provider 不在自动测试中调用。`agent_run` 保存公开检索、分流、引用和结果，但仍不等于不可篡改审计。
当前没有身份隔离，`workspace` 只是输入字段。

### 已有固定问答与 SSE

`dora_chat` 用 `_chat_intent` 匹配关键词，再用 `_compose_answer` 拼接答案。
它可能读到先前 LLM 生成的解释缓存，但该请求本身没有模型规划工具的循环。
旧 `/api/dora/chat` 仍是固定流程；新的完整 RAG 使用独立 `/api/rag/*`，尚未接入这个 SSE 页面。

SSE 是服务器分事件向客户端发消息的一种传输格式。目前代码先完成计算并保存事件，再逐个发送；
它不是逐 token 模型生成，也不是后台任务队列。`thought_step` 是流程状态标签，不是模型内部思维过程。
前端洞察判断区已有 SSE 消费；通用 [AskBar](../../frontend/src/components/dora/AskBar.tsx) 与
[FollowupCard](../../frontend/src/components/dora/FollowupCard.tsx) 仍有静态交互，不能说所有对话入口都已接通。

### 已有第一个只读 Agent 核心

[agent/loop.py](../../backend/app/agent/loop.py) 负责有限循环、预算、停止原因与运行记录，
[agent/tools.py](../../backend/app/agent/tools.py) 是唯一工具允许列表，目前只开放 `query_metric` 与 `search_knowledge`。
模型接口由 `AgentProvider` 协议隔离；当前门禁使用脚本 provider，因此能稳定验证工具选择与失败边界，又不依赖密钥或网络。

这一版能证明执行器闭环已经成立，但还没有真实模型适配器，也没有对最终自然语言答案做引用充分性验证。它不等于可上线的聊天 Agent。

### 专家团尚未成为多 Agent

[builder.py](../../backend/app/action/builder.py) 的默认专家与步骤专家名单，主要是展示和责任分配信息。
目前没有专家注册表、模型实例分工、会商循环或专家工具权限。
可以如实介绍为“预留专家编排方向”，不能介绍为已落地多 Agent 系统。

## 3 按这个顺序练习

以下是教学阶段与当前进度。每次新增能力仍需进入 OpenSpec change。

### A 读懂一次模型调用

**要理解**：请求里有什么、响应如何解析、失败时如何回退。
沿 `resolve_provider → explain → _merge_with_numeric_stability` 阅读，先用假响应测试，理解后再做少量真实调用。

**小练习**：模拟超时、非法 JSON、包含错误数值的输出，观察哪些内容被拒绝、哪些字段保留模板。
**学会的标志**：能解释“模型说了什么”与“最终允许返回什么”的区别，知道现有数字检查的局限。

### B 一个只读工具

**当前状态：第一版已完成。**

**要理解**：工具名称、参数 schema、真实执行函数与返回值之间的关系。
先包装指标查询，例如问题“查看全国最近几条利润率”，模型可以请求 `query_metric`，
程序只允许已有指标、合法维度、有限 limit；未知工具和非法参数直接拒绝。

**小练习**：先直接运行函数，再用一个假的模型工具请求走完校验与执行。
**学会的标志**：能展示工具请求与实际返回的数据，并说明执行不是模型自行访问数据库。

### C 最小 Agent 循环

**当前状态：核心循环已完成，真实模型适配尚未开始。**

现在只有两个只读工具，实际流程如下：

```text
收到用户问题
→ 把问题和工具说明交给模型
→ 若模型请求工具：校验名称与参数 → 执行 → 把结果放回上下文
→ 再请模型决定继续还是回答
→ 完成、超时或达到上限就停止，并记录原因
```

第一版默认最多 4 轮、3 次工具调用；上限由调用方传入，但执行器只接受受限范围。
每轮保存可观察的请求摘要、工具参数、结果引用、错误与结束原因，不要求记录隐藏思维链。
工具异常不能伪造成功；没有数据时应明确说明。

**小练习**：模拟模型连续要求调用工具，确认到上限会停；模拟未知工具，确认不会执行任意函数。
**学会的标志**：能用一条运行记录讲清“为什么查这份数据、查到了什么、为什么停止”。

### D 检索进入答案

**当前状态：第一版已完成。**

先准备少量明确标注为练习材料的口径说明与历史处理记录，保留来源和日期。
当前链路使用词法与向量混合检索，把片段作为不可信的参考材料交给 provider，并要求引用。
以一组固定问题检查找对资料、无资料、相似但不相关资料三种情况，再决定是否需要 embedding。

当前指标来自工具；历史案例中的数值可以在明确历史时间、来源和单位后引用，不能冒充当前事实。
44 篇源文档、40 道固定题和实现结果见 [RAG 整体搭建计划](RAG整体搭建计划.md)。
**学会的标志**：能区分“没检索到”“检索错了”“资料正确但回答错了”。

### E 接前端并评估

**当前状态：后端固定评价已完成，前端入口和真实模型评价未开始。**

接通一个提问入口，让页面呈现“查询中、调用工具、得到答案、失败或停止”。
可以复用 SSE，但要区分真实运行事件与事后回放；取消请求是否取消后台任务需要明确约定。

固定测试集至少包含正常问题、缺数据、错误参数、过期引用、超时、重复调用和恶意资料指令。
记录任务完成情况、引用是否正确、工具调用次数、耗时与模型用量。数字必须来自实际测试，不能预写成绩。
**学会的标志**：能重现失败案例，并用测试证明一次改动改善了什么。

### F 再考虑写工具与多个 Agent

写操作先需要服务端校验、人工确认、幂等和审计；UI 上的确认按钮本身不能代替这些保证。
专家注册表有助于管理角色，但不是实现单 Agent 的前提，也不需要先凑齐十位专家。
只有单 Agent 在固定测试上暴露了明确分工需求，再比较多角色是否改善效果及其额外成本。
不要因为架构图更复杂，就把它当作学习完成度更高。

## 4 旧规划核对与修正

以下结论来自旧 workflow、L1/L2/L3 规划与现有代码的逐项对照。
旧文件原文在 [历史资料](../archive/README.md)；这里替代它们作为当前阅读说明，不改写既有 Spec 契约。

### 保留的方向

规则引擎负责业务判定；工具结果提供事实；模型提出解释和建议；关键写操作由人确认。
证据可回溯、检索有来源、运行可观察、失败有降级、任务有上限，这些都是值得学习的设计目标。

### 需要纠正的内容

1. **“完整 Agent 已有骨架”应拆开说。** 已有接口与日志是真的；模型规划、工具执行循环尚无实现。当前基础不能计作多 Agent 验收。
2. **“无外部 LLM 调用”与代码冲突。** `LLMProvider` 已有网络请求路径。模板模式可以不调用模型，不能据此宣称所有模式都不出网。
3. **“同输入必得同一终态”范围过大。** 确定性要求适用于固定输入、规则和代码版本的引擎；模型措辞、工具选择不承诺逐字一致。工具写入应通过幂等保证效果，而非依赖模型重复生成同一参数。
4. **“9 条洞察”不是任意数据的正确答案。** golden 9 是特定种子基线；清空数据、上传新数据时数量可以改变。旧 workflow 的 `insights.length ≥ 1` 和恒定 9 条只能用于对应夹具。
5. **快照设计输入不全且有生命周期冲突。** 旧哈希遗漏门店集群与引擎版本；旧源行会被替换；“快照永久保留”与样例重置清理也需统一。详细修正放在 [全栈事实基础](../fullstack/README.md#6-与-agent-共用的事实基础)。
6. **RAG 不应一律删除资料中的数字。** 那样会丢掉日期、编号、阈值与历史效果。应区分当前工具事实与历史资料，对来源、时间、单位和适用范围做校验。改变现有数字锁契约须另立 spec delta。
7. **数字白名单不等于事实正确。** 一个数字即使出现在输入里，也可能属于另一门店或另一日期；单位、主体、比较方向和引用是否支持结论都要检查。当前 `_merge_with_numeric_stability` 保留 causeA/causeB 的 value，但 name 与 next 仍接受模型文本，不能宣称全部数字都已被校验。现有启发式 confidence 也不是答案正确率。
8. **schema 没有数值字段不能保证文本不含数字。** `text`、`actions` 等字符串仍可产生错误陈述。需要受限输出、后处理、引用校验和失败回退；不能宣称已从结构上杜绝幻觉。
9. **权限与工具约束不能等到多 Agent 完成。** 第一个工具执行器就需要允许列表、参数校验、超时和结果范围限制。接入共享用户或真实数据前再补相应身份隔离。当前 CORS 不是认证，也不保证服务只在内网可访问。
10. **提示注入没有单条万能护栏。** 用标签包裹材料、屏蔽“忽略”一词都不能证明安全。参考资料不得成为授权来源，模型不能自行增加工具权限，写入必须经过独立校验。安全结论需由具体攻击测试支撑。
11. **专家注册表、四槽检索、向量库不是第一步。** 先做小型只读循环和检索评估，再用失败样例决定是否需要它们。RRF 也不是无需调参或一定更准的保证。
12. **会商结果应可保存为过程。** 未验证的模型结论不能自动变为可信知识；人工审核并保留来源后可以作为新知识候选，不必规定永远不得入库。沿用当前业务验证边界，变更需走 Spec。
13. **Dify 长配置只能作为旧参考。** 本仓库没有可证明该整套工作流已部署的运行证据；本文没有验证具体 Dify 版本的节点/API 兼容性。先理解 Python 中的最小链路，选用 Dify 时再按当时官方文档导入、逐节点实测，不能照抄后宣称完成。
14. **运行日志不等于不可篡改审计。** 现有 `agent_run` 没有完整身份、版本锁定和审计控制；SSE 传输也不自动带来任务队列、重试、断点续跑或可靠取消。

## 5 什么属于全栈 什么属于 Agent

数据上传、存储、规则判断、事实快照、事务、Action/Watch 状态机，都在 [全栈区](../fullstack/README.md)。
模型消息、工具描述、调用循环、检索上下文、模型输出校验与评估，在本区。
两者通过受控工具接口连接：Agent 使用已有业务能力，不能另写一套利润率判定来覆盖引擎。

## 6 学习时怎么讲清楚

能解释一次模型请求，不等于已完成 Agent；能运行一条有真实工具结果的有限循环，才完成本文的核心练习。
每个阶段都准备一个成功例子、一个失败例子和对应代码位置。
面试内容随真实实现更新，参考 [面试项目技术说明](../面试项目技术说明.md)。

## 7 可迁移到其他项目的一般化搭建流程

这套顺序不依赖 Dora，也不依赖某个 Agent 框架：

1. **先选一个小问题。** 明确用户会问什么、答案依赖哪份真实数据、什么结果算完成。第一版避免写操作。
2. **把业务能力做成普通函数。** 先直接测试“给定参数 → 返回真实结果”，不要一开始就接模型。
3. **定义工具契约。** 为每个函数写名称、用途、参数 schema、允许值、返回上限和无数据语义。工具注册表是唯一允许列表。
4. **实现确定性执行器。** 先检查工具名与参数，再执行；模型只有提议权。错误、超时和空结果都返回结构化状态。
5. **加入有限循环。** provider 每轮只能返回“调用工具”或“最终回答”；设置轮数、工具次数和总时长上限，并给每种停止原因命名。
6. **从开始就记录运行。** 保存输入、校验后的调用、工具结果或引用、错误、最终输出和停止原因；不要保存或展示模型隐藏思维链。
7. **先用假模型验收。** 固定脚本覆盖正常、无数据、未知工具、非法参数、重复调用、工具故障和 provider 故障。这样失败时能分清是循环问题还是模型波动。
8. **再接一个真实模型。** 适配器只负责把供应商响应转换成统一决策；补超时、重试、用量、模型版本和输出引用校验。少量真实调用不能替代固定回归。
9. **最后接界面与写工具。** 页面展示公开运行事件；写操作在服务端另加身份、授权、人工确认、幂等和审计，不能直接复用只读权限。

在本项目中，对应代码入口是：工具注册表 → [tools.py](../../backend/app/agent/tools.py)，循环 → [loop.py](../../backend/app/agent/loop.py)，确定性验收 → [agent_loop_check.py](../../backend/tests/agent_loop_check.py)。运行时使用独立测试库：

```bash
cd backend
python -m tests.agent_loop_check
```
