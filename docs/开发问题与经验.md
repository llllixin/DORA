## P001｜打开 .tsx 满屏红波浪线 / Cannot find module

- **现象**：VS Code 打开任意 `.tsx` 都报大量 `Cannot find module 'react'` 之类错误，几乎每个文件都红
- **原因**：依赖从未安装，`node_modules` 不存在；TypeScript 语言服务读不到第三方包的类型声明，连锁报错
- **解决**：`cd frontend && npm install`；若装完后编辑器红线未消失 → `TypeScript: Restart TS Server` 或 Reload Window
- **教训 / 原则**：拿到任何前端工程（生成/克隆）第一步先确认 `node_modules`；"满屏红"先查"是不是没装依赖"，别先怀疑代码

## P002｜`Property 'env' does not exist on type 'ImportMeta'`

- **现象**：装完依赖后类型检查仍剩 1 个错：`doraApi.ts` 使用 `import.meta.env.VITE_API_BASE_URL` 报类型不存在
- **原因**：项目缺 Vite 标配的类型声明文件 `src/vite-env.d.ts`，TS 不识别 `import.meta.env`
- **解决**：新建 `frontend/src/vite-env.d.ts`，内容一行 `/// <reference types="vite/client" />`
- **教训 / 原则**：`import.meta.env`、`*.css` 模块等 Vite 特性需要类型声明支撑；看到"类型不存在"先想"是不是少了类型声明文件/依赖"，可能是工程缺文件而不是代码错

## P003｜`npm run build` 卡在 `tsc -b`

- **现象**：构建在类型检查阶段就中断，Vite 打包根本没跑
- **原因**：package.json 的 build 脚本是 `tsc -b && vite build`，类型检查不过不会进入打包
- **解决**：先跑 `npx tsc -b` 把类型错误清干净再 build（P002 即由此暴露）
- **教训 / 原则**：build = 类型检查 + 打包两段；报错位置在 `tsc` 段时不要去找打包问题，先看 TS 错误

## P004｜编辑器整段替换失败："text not found"

- **现象**：对 `App.tsx` 做大段/全文件替换时匹配不到旧文本
- **原因**：文件在两次读取之间被格式化工具改写了排版（压缩单行 → 多行、引号风格变化），手里的"旧文本"已过期
- **解决**：重新 `read` 当前真实内容，改用**小锚点分片替换**（imports / 函数签名 / 单条 JSX 属性等唯一片段），不再整文件覆盖
- **教训 / 原则**：批量编辑前先重读文件确认格式；编辑后读回验证；大改动拆成唯一锚点的小步提交，失败面小、好回滚

## P005｜编辑误删类型定义（手工失误）

- **现象**：给 `types.ts` 追加类型时用整行替换，误把 `ChartPointSeries` 原定义删掉，`ChartData` 连锁报类型错误
- **原因**：替换操作的新文本里漏带了原行
- **解决**：发现后立即读文件比对，恢复原定义，随后重新构建验证
- **教训 / 原则**：替换型编辑务必把"要保留的原行"写进 new_text；每次改动后都跑一次类型检查，能在 1 分钟内暴露这类误伤

## P006｜本地服务打不开 / 被代理影响

- **现象**：shell 配了 HTTP/SOCKS5 代理（`127.0.0.1:7898`），担心访问 `localhost:5173` 受影响
- **原因**：代理只作用于"出网流量"；本地回环服务不受代理环境变量影响。真正的风险点是 curl 会把 localhost 也送进代理，或代理软件劫持了 localhost
- **解决**：curl 用 `--noproxy '*'` 验证；浏览器打不开时改用 `http://127.0.0.1:5173/` 或在代理软件 Bypass 列表加 `localhost;127.0.0.1`
- **教训 / 原则**：本地联调 = 回环流量，与代理无关；遇到"装好却访问不到"先分清是代理劫持还是服务没起

## P007｜产品流程假设了数据已存在（冷启动缺口）

- **现象/洞察**：搭建文档 MVP 流程是"打开 Dora → 看到业务脉搏"，但它默认数据已在系统里；真实产品第一次打开没有任何数据
- **讨论结论**
  1. "上传要等整个系统跑通"是**伪依赖**——"数据入口（上传/解析/落库）"和"上传后自动触发分析引擎"可以解耦
  2. 首屏应为**无数据引导 + 上传/样例选择**，并把上传当作整条价值链的第 0 环（Data 是核心循环的起点）
  3. 上传不是一次性 onboarding：日常"更新数据"复用同一入口（对应文档中 09:32 数据更新场景）
- **落地**：迭代 3 前端 mock 版（引导页 → 数据就绪 → 业务脉搏；更新/清除入口），真实解析随后端接
- **教训 / 原则**：Demo 流程 ≠ 产品流程；凡"数据驱动的 AI 产品"都要先回答"数据第一次从哪里来、空状态长什么样"，它属于闭环起点而不是收尾功能；开发顺序上优先做"竖切（上传本身）"，把"完整流水线触发"交给引擎阶段

## P008｜vite.config 代理改动没生效，且端口被残留进程占用

- **现象**：给 `vite.config.ts` 加了 `/api` 代理后，`curl localhost:5173/api/health` 返回的是前端 HTML（SPA fallback），不是后端 JSON
- **原因**：正在运行的 dev server 未重新加载新配置（Vite 配置改动不一定热重启）；同时旧 dev 进程未被清理，新起服务自动 fallback 到 5174
- **解决**：杀掉占用 5173/5174 的所有进程 → 重新 `npm run dev` → 再次 curl 验证代理返回 `{"status":"ok"...}`
- **教训 / 原则**：改动 `vite.config.ts` 后**主动重启 dev server** 并用 curl 验证；重启前用 `lsof -ti tcp:5173 | xargs kill` 清干净端口，避免出现"明明起了新服务却在 5174"的假象

## 通用经验速查

1. 前端新工程 → 先 `npm install`；编辑器还红 → Restart TS Server。
2. Vite 工程一定保留 `src/vite-env.d.ts`；类型错误先怀疑"缺声明/缺依赖"。
3. `npm run build` 的报错段位（tsc / vite）决定排查方向。
4. 编辑文件前重读真实内容（可能被格式化改写）；用唯一锚点做小步替换；改完读回 + 构建。
5. 本地回环服务不受终端代理影响；联调问题先排除代理劫持。
6. 产品闭环从"数据入口 + 空态"开始，别让 Demo 的"数据已存在"假设掩盖冷启动需求。
7. Mock 与真实 API 边界（`doraApi.ts`）保持清晰，功能演示推进不阻塞后端演进。
8. 改 `vite.config.ts` 要手动重启 dev server 并 curl 验证；重启前清空端口，防止服务悄悄换到 5174。
9. 前后端字段契约用同一套命名（camelCase），后端种子数据与前端 `data.ts` 保持同源，替换数据源时 UI 零改动。
10. 对"单行超长组件"的改造：不要硬上全量 prop 注入；可用"数据层原位同步（同一引用 mutate + 重渲染）"过渡，视觉零风险，等后端引擎接管判断字段后再切正式契约。
11. 追加/编辑列表类文档时优先用"在结尾插入"，别用"替换上一行"的写法（P005 已因此误删一次，教训通用化）。

### D001｜技术栈与工程形态选型

- **时间**：2026-09-06（仓库基线）
- **决策**：把单文件 v9 HTML Demo 迁移为 React 19 + TypeScript + Vite 的 feature-based 前端；后端用 FastAPI 起步并保留 PostgreSQL / Redis / Agent 的工程边界。
- **为什么**：单文件 Demo 无法接真实数据、无法多人协作、无法演进出 Agent/调度；文档《完整详细的搭建说明流程.md》明确目标是"可运行、可演进、可接真实业务与 Agent 的产品"。
- **影响与代价**：前端承担了 Demo 的全部展示/交互；后端判断能力需逐步补齐。feature 目录（pulse/insight/action/watch）成为领域语言。
- **状态**：生效。

### D002｜冷启动是产品第 0 环

- **时间**：2026-09-06（迭代 3）
- **决策**：无数据时首屏是"数据引导页"（上传 / 载入样例），数据就绪后才进入业务脉搏；Topbar 提供"更新数据/清除"入口。
- **为什么**：搭建文档 MVP 流程隐含"数据已存在"，但真实产品第一次打开没有任何数据；上传是价值链 `Data→…` 的起点，不是收尾功能。
- **影响与代价**：前端增加 localStorage(`doraDataSource`) 门禁；"上传后自动触发分析"的最后一公里要等后端 Ingest 接通。
- **状态**：生效；后端真实上传解析（`POST /api/datasets`）待接入。

### D003｜演示模式的"假上传"诚实标注

- **时间**：2026-09-06（迭代 3）
- **决策**：自定义上传只取文件名并走内置样例运行完整流程，界面明确提示"真实解析随后端上线"；不假装真的解析了 xlsx。
- **为什么**：给用户/评审"假解析成功"的错觉，比少一个功能更伤信任。
- **影响与代价**：功能不完整是可见的，但换来诚实的产品边界。
- **状态**：生效。

### D004｜API 字段契约 camelCase、种子同源

- **时间**：2026-09-06（迭代 4）
- **决策**：后端 Pydantic 字段与前端 TS 类型保持**同一套 camelCase 命名**（`rawRows/caseTitle/tagCls`）；后端 `data.py` 镜像前端 `data.ts`。
- **为什么**：契约一处定义、两端共享语义，前端切换数据源时**零适配层、零 UI 改动**；避免 JSON 里再来一层 snake↔camel 映射。
- **影响与代价**：牺牲了后端惯例 snake_case；若未来对外部开放 API 再评估是否加映射层。
- **状态**：生效。

### D005｜API 三模式 auto / mock / http

- **时间**：2026-09-06（迭代 4）
- **决策**：`doraApi.ts` 支持 `VITE_API_MODE`：`auto`（HTTP 优先、失败静默回退 Mock）、`mock`（不请求）、`http`（失败抛错）。
- **为什么**：默认 auto 保证"没后端也能演示、接上后端立刻真实"；联调/排障用 http 让问题第一时间暴露，而不是被回退掩盖。
- **影响与代价**：auto 模式下生产环境若后端挂掉会静默降级，需在部署时用 `http` 或监控兜底。
- **状态**：生效。

### D006｜页面导航用 URL hash

- **时间**：2026-09-06（仓库基线）
- **决策**：不引入 react-router，用 `location.hash`（`#page=&type=&idx=`）+ `hashchange` 恢复页面上下文。
- **为什么**：Demo 页面层级浅、依赖少、刷新/分享可恢复；避免为 4 个页面引入路由全家桶。
- **影响与代价**：未来若做深层路由/懒加载需评估是否换 react-router（触发器：页面数 > 8 或需要嵌套路由/守卫）。
- **状态**：生效。

### D007｜行动/关注状态暂存 localStorage

- **时间**：2026-09-06（仓库基线）
- **决策**："已加入行动回路"清单存在 `localStorage`（`doraJoinedAction`），不依赖后端。
- **为什么**：后端状态模型尚未落地；用本地持久化先把"加入→执行→回写"的交互跑通，演示不因刷新丢失。
- **影响与代价**：这是**临时状态源**，V2 状态模型（action_case/action_step 表）落地后需迁移并做双写兼容。
- **状态**：生效（待迁移）。

### D008｜页面切 HTTP 采用"原位同步"，不硬拆组件

- **时间**：2026-09-06（迭代 5）
- **决策**：不把 Pulse/Insight/Action/Watch 改造成"prop 注入 + 加载态"，而是 App 启动同步器把后端列表**原位刷新**到 `data.ts` 同一批数组/对象再触发重渲染。
- **为什么**：这些页面是超长压缩单行组件，硬拆会带来大改动与回归风险；同步器模式让页面"无感"切换为后端数据，视觉与契约不变。
- **影响与代价**：`data.ts` 仍是前端双写源，架构上是过渡态；等 V2 引擎把判断字段上移到后端后，再按正式契约重构组件（见 D011）。
- **状态**：生效（过渡态）。

### D009｜稳定前不引入 Agent / LLM / Redis 调度

- **时间**：2026-09-06（基线约定，持续生效）
- **决策**：在业务对象、数据流、Rule/Signal/Insight 引擎稳定前，不引入 Agent / LangChain / MCP / Redis 定时调度。
- **为什么**：搭建文档第 29 章明确警告——先跑通确定性规则与业务对象，再谈智能编排，否则复杂度失控。
- **影响与代价**：功能上"AI 味"暂时不足；但换来可测试的引擎与可解释的证据链。
- **状态**：生效（触发器：Metric→Rule→Signal→Insight 链路在 PostgreSQL 上跑通后，才进入 Reasoning 阶段）。

### D010｜后端先 Mock Repository，再上 PostgreSQL

- **时间**：2026-09-06（迭代 4）
- **决策**：FastAPI 端点先返回内存 Mock Repository（`app/data.py` 镜像前端数据），不直接连 PostgreSQL。
- **为什么**：先把 API 契约与前端消费打通，DB 迁移不阻塞契约验证；符合"一次只引入一个变化"的原则。
- **影响与代价**：数据重启即丢；PostgreSQL + SQLAlchemy 层是明确的下一个后端任务。
- **状态**：生效（待替换）。

### D011｜演示语义字段暂留前端

- **时间**：2026-09-06（迭代 5，明确限制）
- **决策**：Pulse 摘要数字（3/2/4/6）、Insight 的原因/下一步建议、图表数据等"判断语义"暂时留在页面内，不搬到后端。
- **为什么**：这些文案本质是"后端判断结果"，但 V2 Insight Engine 尚未存在；现在搬运=在后端复制死数据，无增益且与 D009 冲突。
- **影响与代价**：前端仍有"判断残留"，违反长期边界原则；D011 的**退出条件**= V2 引擎上线并扩展 `GET /api/insights/{id}` 详情契约。
- **状态**：生效（明确为临时）。

### D012｜构建产物重定向，杜绝过期配置与脏提交

- **时间**：2026-09-06（git 基线时发现并修复）
- **决策**：`tsconfig.app.json`/`tsconfig.node.json` 的 `tsBuildInfoFile` 与 node 的 `outDir` 全部指向 `node_modules/.tmp`；`.gitignore` 兜底忽略 `*.tsbuildinfo`、`vite.config.js/.d.ts`。
- **为什么**：`tsc -b` 曾在前端根目录生成 `vite.config.js`（过期生成物，可能覆盖手写 `.ts` 被 Vite 优先加载）与 tsbuildinfo（污染首次提交）；重定向后仓库干净、配置单一事实源。
- **影响与代价**：构建增量缓存挪到 git 忽略区；无功能影响。
- **状态**：生效。

### D013｜Git 基线：本地身份 + 每功能点一提交

- **时间**：2026-09-06
- **决策**：仓库 `git init`（main 分支），身份仅写入本仓库（`tomara <tomara@mac>`，全局不动）；约定后续每个功能点/文档变更独立提交。
- **为什么**：此前没有版本控制，无法回滚与对比；小粒度提交让"实际开发过程记录"与 commit 一一对应，便于回放每个迭代。
- **影响与代价**：本地身份不用于 GitHub 提交时需另配；推送远程前确认身份与远程仓库地址。
- **状态**：生效。

### D014｜V2 引擎先于 PostgreSQL / LLM：确定性计算先行
