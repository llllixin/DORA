### 3D.1 前端接线收口（change 前缀 `frontend-loop`）

> 定位一句话：消灭「页面写死业务判断 / 占位动作 / 静默 toast」，让 Pulse/Insight/Sidebar/Topbar/EvidenceDrawer 的**呈现与动作全部连到后端真实数据，或明确禁用+标注原因**；data.ts 只保留「离线演示」兜底语义。
> 现状证据（2026-09-08 审计）：Action/Watch/Knowledge/洞察列表/证据链/上传/重新解释已真连；剩余占位集中在 Pulse 子面板、Insight 页静态回退字典、Sidebar/Topbar/EvidenceDrawer 固定入口、AskBar/FollowupCard 追问（F8，另立）。

**范围（In scope）**
- Pulse 页真实化：Summary/优先级主区/问题栈/信号板/监控卡全部读 `/pulse` + `/insights` + `/watch`（引擎同源）；删除组件内写死的 view/signal/monitor/信号文案字典，文案由 desc/semantics/evidence 字段拼接。
- Insight 页静态回退字典下线：cause/next/n 只从 `semantics`（reasoning 下发）取；无 semantics 时显示「模板未覆盖」而非编造数字。
- Pulse「让 Dora 帮我跟进」→ 真实建 Watch 委托（p1 利润率 → `关注利润率…`）；按钮态与结果回写跟随 `/watch`。
- 框架接线：Topbar 证据入口跟随当前洞察（不再固定 p1）；Sidebar「Dora发现 n」读 `/pulse` 计数；EvidenceDrawer「定位原始数据」连 `/evidence/{id}`（path 不可定位则诚实禁用）。
- 离线边界显式化：detectApi 失败 → 顶栏「离线演示」标识；动作按钮要么真实调用、要么明确提示本地兜底，杜绝静默成功。
- 轮询补齐：Pulse/Insight 纳入 20s 轻量轮询（与 Watch/Action 一致，F7 语义）。

**非目标（Out of scope）**
- AskBar/FollowupCard「追问」真实化（F8 = Dora Chat 候选，另立规划，不夹带）。
- 图表由引擎数据驱动（F11）：需后端 series/趋势导出端点，单列候选。
- Action/Watch/Knowledge 域行为改动；专家注册表/编排编辑（归 3D.2）。

**接口（复用现有，预计零新增端点）**
```text
GET  /api/pulse            # Summary/计数
GET  /api/insights?type=   # problem/opportunity/change（含 semantics/reasonSource）
GET  /api/watch            # 监控卡与「持续关注」卡
GET  /api/evidence/{id}    # EvidenceDrawer 定位
POST /api/watch            # Pulse「让 Dora 跟进」建档（解析失败→显式 400 提示）
GET  /api/knowledge        # Sidebar 计数（可选）
```

## 4. 已选 backlog · 3D.2 专家团领域化（change 前缀 `expert-registry`，E1–E3，多 agent 前置）

### 3D.2 专家团领域化（change 前缀 `expert-registry`，多 agent 前置）

> 定位一句话：把「专家」从字符串标签（`orchestration.experts`）升级为**专家注册表实体**——id/角色/适用域/口径范围/能力描述/未来 agent 挂载位；建档引擎按 kind+metric 自动组队，Action 页可人工增补，Pulse/Sidebar 同源展示。为候选方向 §1「P2-7 工具/Agent 执行层」提供挂载底座（D031-1 预留口），红线延续 D009/D029/D031。
> 现状证据：专家散在 4 处且只是名字（`data.ts capabilities.专家团` / `autoExpertNotes` / `app/action/builder.py ORCH_DEFAULTS` / seed 静态档案 orchestration），无实体、无能力描述、Action 页只读「系统已选」不可增补。

**范围（In scope）**
- 域对象 + 持久化：新增 `expert` 表（expert_id、name、role、适用 kind=problem|opportunity|all、scope 指标口径、abilities、desc、agent 挂载字段可空）+ Repository CRUD + 幂等 seed（内置 ≥10 位：经营分析/财务/销售/门店运营/供应链/会员运营/经营增长/商品/数据分析等，覆盖现 5 档案 6 类引用并扩充）；新建能力 spec `business-expert`。
- 建档引擎自动选团：`builder.ORCH_DEFAULTS` 静态常量 → 按 kind+命中 metric 查 registry（无命中回退 kind 默认组，幂等）；seed 5 档案 orchestration 保留原值不改观感。
- Case 编排 API：专家只读列表 + 推荐团 + 编排回写（校验专家存在；只写 orchestration 元数据，**不回写判定/不伪造执行**）。
- 前端：Action 档案「专家团」chips 可增删（选择器读 registry，区分「系统已选/我增补」）；Pulse「专家团能力说明」与 Sidebar CapabilityPanel 读同一 registry（消灭 data.ts 双源；data.ts 仅保留标注「离线镜像」的兜底）。

**非目标（Out of scope）**
- 真实 agent 运行时/工具调用/自动执行（P2-7：需本块 sign-off 后另立版本规划；专家只提供挂载位，agent 字段恒 null 直到 P2-7）。
- AskBar/Chat 追问（F8）；Watch/Action 判定语义改动。
- 编排「自动执行步骤」：仍人/工具回填 note（D031 红线）。

**接口（新增，契约草案）**
```text
GET  /api/experts                       → { ok, experts:[{ id,name,role,kind,scope[],abilities[],desc,agent }] }   # 只读目录
GET  /api/experts/suggest?kind=&metric= → { ok, experts:[...] }            # 建档/详情页推荐组（builder 同源算法）
PUT  /api/action/cases/{id}/orchestration { experts:[id,...], data:[...] } # 校验专家存在；非法 400；回写持久化
GET  /api/action/cases/{id}             → orchestration 内嵌专家 id+name+role（兼容现前端结构）
```

**任务（每项 = 一个 OpenSpec change，按序开工）**
| 任务 | 内容 | 输出/验证 |
|---|---|---|
| E1 `expert-registry-domain` | expert 表 + Repository CRUD + seed 目录（≥10）+ `GET /api/experts` + 新建能力 spec `business-expert` + 归档索引/README | 空表 CRUD/幂等 seed；curl /api/experts 断言 ≥10 位含 id/role/kind/agent=null；run_all 保持绿（新增 expert_check 段） |
| E2 `expert-registry-orchestration` | builder 静态 ORCH_DEFAULTS → registry 建议组（kind+metric）；`PUT …/orchestration` 校验/回写；seed 5 档案编排不变 | 断言 builder 不再引用 ORCH_DEFAULTS 常量；PUT 非法专家 400/合法回写持久化；action_check/e2e 不回归 |
| E3 `expert-registry-ui` | Action 专家 chips 可增删；Pulse/Sidebar 能力说明同源展示；档案详情显示角色/范围 | `npm run build` 绿；页面冒烟（后端在线=registry、离线=镜像标注）；curl 编排读写一致 |

**红线与验收计划**
1. 专家只描述「谁适合处理什么」（orchestration 元数据），不持有判定权、不回写引擎判定/reasonSource（V3–V5 红线延续）。
2. agent 挂载位默认 null，UI/API 不暗示已可自动执行（诚实边界，D031-1/P2-7 之前）。
3. 新增专家 scope 建议属于引擎支持指标口径（D029 语义），不满足则标注「展示用」，不假装可调度。
4. 单一事实源：Pulse/Sidebar/Action 专家内容只读 registry；data.ts 仅离线镜像（注明）。
5. 回归锚点：run_all ≥8 段（新增 expert_check）ALL GREEN、golden 9 不变、`npm run build` 绿。

**进入条件**：V1–V5 门禁全绿（已满足）。E1 开工即走 opsx-propose（首个归档新建能力 spec `business-expert`）；E2/E3 依赖 E1；E3 的 Pulse/Sidebar 同源子项同时解锁 3D.1-W3 对应子项。P2-7 工具/Agent 执行层需本块 sign-off 后另立版本规划再开工。

**补强要求（2026-09-08 审查，apply 前必须并入 proposal）**
1. E2 明确历史 seed 5 档案与新档案的两套编排一致性策略（建议同 kind+metric 稳定输出专家组），并加 builder 断言。
2. knowledge 的 `change` 类型在出现真实写入方前，前端可去掉该恒 0 chip 或写明未来写入时机。
