# Dora · AI 主动经营驾驶舱
# 完整详细的搭建说明流程

> 版本基线：最新 v9 产品 Demo
> 
> 目标：把“单文件交互 Demo”升级成可以真正运行、持续演进、可以接真实业务数据与 AI Agent 的全栈产品。

---

## 0. 先把 Dora 讲清楚：它到底是什么

Dora 不是传统 Dashboard。


Dora 的基本动作应该是：

```text
业务数据更新
    ↓
Dora 理解数据
    ↓
建立业务口径
    ↓
检测趋势 / 阈值 / 结构变化
    ↓
判断“什么值得关注”
    ↓
形成问题 / 机会 / 变化
    ↓
组织证据
    ↓
给出判断
    ↓
给出下一步
    ↓
把问题 / 机会变成行动回路
    ↓
把变化变成持续关注
    ↓
持续验证结果
    ↓
结果回写
    ↓
新的数据再次进入循环
```

所以 Dora 最核心的产品公式是：

```text
Data
→ Metric
→ Rule
→ Signal
→ Insight
→ Evidence
→ Reasoning
→ Recommendation
→ Action / Watch
→ Verification
→ Feedback
→ New Data
```

这是整个项目所有代码、数据库、Agent、定时任务的共同主线。

# 1. 最新 Demo 必须被保留的产品逻辑

本项目以最新 v9 Demo 为产品事实基线。

最新 Demo 已经明确表达了几个非常重要的产品决策：

### 1.1 业务脉搏是入口，不解决所有问题

首页回答：

> 今天，有什么业务值得你关注？

首页负责“发现 + 排序 + 导航”，而不是把所有分析内容塞在一个 Dashboard 里。

页面结构为：

```text
业务脉搏
├── 需要处理
├── 增长机会
├── 重要变化
├── 持续关注
│
├── 今日经营主线
│   └── P1 主问题
│
├── 业务脉络 · 问题
│   ├── P1
│   ├── P2
│   └── P3
│
├── Dora 监控状态
├── 本轮 Dora 工作
│
├── 其他经营信号
│   ├── 机会
│   └── 变化
│
└── 问 Dora
```

这意味着前端需要把首页定位成“经营注意力入口”，后端需要生成一个排序后的业务脉络，而不是单纯返回 KPI。

# 2. 三类 Insight 是三种不同业务语义

Dora 当前不是简单的：

```text
红色 / 绿色 / 蓝色
```

而是三种不同的判断流程。

## 2.1 Problem：问题

问题需要回答：

```text
发生了什么？
为什么发生？
影响有多大？
是否可干预？
下一步应该处理什么？
```

问题典型链路：

```text
异常指标
  ↓
连续性 / 阈值判断
  ↓
影响评估
  ↓
因素归因
  ↓
形成问题 Insight
  ↓
进入 Action Loop
```

例如：

```text
利润率连续 3 天低于目标
        ↓
A 产品线成本上涨
        ↓
供应商 B 采购价格上涨
        ↓
预计利润影响约 ¥230,000
        ↓
核查供应商 B
        ↓
形成 PRF-0831
```

---

## 2.2 Opportunity：机会

机会不能简单理解成“指标上涨”。

必须回答：

```text
增长来自哪里？
是不是结构性增长？
是不是可复制？
哪些对象做对了？
值得不值得投入资源放大？
```

典型链路：

```text
正向趋势
  ↓
来源拆解
  ↓
贡献因素排序
  ↓
相似对象 / cohort
  ↓
识别共同动作
  ↓
机会 Insight
  ↓
进入 Action Loop
  ↓
小范围试点
  ↓
验证可复制性
  ↓
扩大推广
```

例如：

```text
客单价连续 4 周增长
        ↓
新品贡献 62%
        ↓
找高增长门店
        ↓
提炼共同经营动作
        ↓
选 3 家相似门店试点
        ↓
验证后复制
```

---

## 2.3 Change：变化

变化是整个产品最关键的“中间态”。

变化不是问题，也不是机会。

变化回答的是：

> “这件事发生了，但现在值得升级吗？”

典型链路：

```text
指标变化
  ↓
趋势观察
  ↓
阈值判断
  ├── 未达到阈值 → Watch
  ├── 持续正向 → Opportunity
  └── 持续恶化 → Problem
```

所以：

```text
Change ≠ Alert
Change ≠ Problem
Change = Observation State
```

例如：

```text
华东订单量下降 1.8%
        ↓
升级阈值 = -3%
        ↓
还没到阈值
        ↓
加入持续关注
        ↓
如果未来继续跌
        ↓
自动升级为 Problem
```

这套逻辑必须体现在后端规则引擎里，而不能只写在前端按钮文本里。

---

# 3. Evidence Chain 是 Dora 的可信度基础

Dora 最大的问题不是“能不能生成一句漂亮的话”。

而是：

> “这句话为什么是真的？”

所以任何重要 Insight 都必须存在独立 Evidence 对象。

Evidence 至少包含：

```text
source
updated_at
sheet / table
scope
metric_definition
hit_records
query_path
fact
judgment
suggestion
```

最终用户看到：

```text
洞察
  ↓
证据范围
  ↓
原始数据定位
  ↓
分析路径
  ↓
事实
  ↓
判断
  ↓
建议
```

而不是：

```text
AI：我认为主要原因是供应商 B
```

# 6. Frontend 工程搭建

第一阶段：



# 7. Pulse 页面实现思路

Pulse Page 的数据接口不要直接返回一大坨 HTML 所需要的数据。

建议 API 返回：

```json
{
  "summary": {
    "problems": 3,
    "opportunities": 2,
    "changes": 4,
    "watching": 6
  },
  "priority": {
    "insight_id": "p1"
  },
  "signals": [],
  "monitor": {},
  "agent_run": {}
}
```

前端负责：

```text
数据 → 展示
```

后端负责：

```text
什么是 P1
为什么排序第一
为什么归类为 Problem
```

# 8. Insight 页面实现思路

Insight 页面是整个前端最复杂的页面。

它必须支持：

```text
Tab 切换
Insight List
Insight Detail
不同图表
不同 evidence
不同 confidence
不同 next steps
不同升级路径
```

不能写一个：

```text
<GenericInsightPage />
```

然后所有 insight 都填不同数字。

应该至少把语义作为数据模型明确出来：

```ts
interface Insight {
  id: string
  type: 'problem' | 'opportunity' | 'change'
  title: string
  description: string
  confidence: number
  metric: string
  delta: string
  source: string
  nextSteps: string[]
  route: 'action' | 'watch'
}
```

目前 Demo 使用 SVG，是合理的第一阶段选择。

```text
演示快
```

# 10. Action Loop 数据结构

行动回路应该是独立领域对象。

核心对象：

```text
ActionCase
ActionStep
Execution
ResultSnapshot
```

关系：

```text
Insight
  ↓
ActionCase
  ↓
ActionStep[]
  ↓
Execution
  ↓
ResultSnapshot
  ↓
Verification
```

例如：

```text
PRF-0831
│
├── 发现问题
├── 定位原因
├── 当前行动
├── 持续验证
└── 问题解决
```

注意：

“问题解决”不是用户点击一个按钮结束。

应该由结果验证决定：

```text
利润率是否恢复？
       ↓
是 → Case Closed
否 → Continue Monitoring
```

---

# 11. Watch / 持续关注数据结构

Watch 不是告警配置中心。

而是一个：

> Business Goal Delegation

对象应该类似：

```text
WatchTarget
├── metric
├── scope
├── condition
├── frequency
├── escalation_rule
├── data_sources
├── current_state
└── next_check_at
```

例如：

```text
目标：华东订单量
指标：订单量
范围：华东
条件：连续 3 天下降
频率：每日 09:00
升级：跌破 -3%
```

---

# 12. Watch 的核心不是“报警”，而是“升级”

真正逻辑应该：

```text
Watch Target
     ↓
Scheduled Check
     ↓
Metric Snapshot
     ↓
Rule Evaluation
     ↓
      ┌───────────────┐
      │               │
      ↓               ↓
  未变化           发生变化
      │               │
      ↓               ↓
继续观察        创建 Change Event
                        ↓
                  Insight Engine
                        ↓
                ┌──────┴──────┐
                ↓             ↓
             Problem      Opportunity
                │             │
                └──────┬──────┘
                       ↓
                  Action Loop
```

这样 Watch 才真正融入闭环。

# 15. Metric Definition

Metric 不应该只存：

```text
profit_margin
```

而应该记录：

```text
id
name
code
definition
formula
unit
owner
version
active
```

例如：

```text
name = 利润率
formula = profit / sales_amount
unit = %
```

原因：

同一个“利润率”不同部门可能口径不同。

Evidence 必须引用一个确定版本的 Metric Definition。

---

# 16. Rule Engine

Rule 是 Dora 主动判断的基础。

不要把所有判断都交给 LLM。

应该分成：

```text
Deterministic Rule
+
Statistical Detection
+
LLM Reasoning
```

例如：

```text
规则：
利润率连续 3 天 < 18.5%
```

这个应该由程序判断。

而：

```text
为什么主要是供应商 B？
```

才交给分析模型。

---

# 17. Signal Engine

Signal 是 Rule 输出和 Insight 输入之间的一层。

例如：

```json
{
  "id": "sig-001",
  "metric": "profit_margin",
  "current": 18.7,
  "baseline": 20.8,
  "direction": "down",
  "severity": "high",
  "rule_id": "profit-margin-below-target",
  "occurred_at": "2026-09-03T09:32:00"
}
```

Signal 不等于 Insight。

Signal 是：

> “发生了什么”

Insight 是：

> “这意味着什么”

---

# 18. Insight Engine

Insight Engine 负责把多个 Signal 组织成一个业务判断。

例如：

```text
Signal A
利润率下降

Signal B
A 产品线成本上升

Signal C
供应商 B 采购价上升

Signal D
利润影响超过阈值

        ↓

Insight
“利润率正在失速”
```

这一步不要让 LLM 一个人决定所有东西。

程序先组织 Context，LLM 再做解释和语言表达。

# 19. Dora Agent 的真正思维链

Dora Agent 推荐采用：

```text
Intent
  ↓
Context
  ↓
Plan
  ↓
Tool Selection
  ↓
Data Retrieval
  ↓
Evidence Assembly
  ↓
Reasoning
  ↓
Recommendation
  ↓
Action / Watch Routing
```

### Intent

判断用户在问：

```text
为什么？
是什么？
有哪些机会？
帮我持续关注
帮我处理
给我证据
```

---

# 20. Agent Context

Agent 上下文不能只是一段 chat history。

应该至少包含：

```text
workspace
current_page
current_insight
current_action
current_watch
selected_metric
selected_region
user_question
```

例如：

```json
{
  "workspace": "门店经营",
  "page": "insight",
  "insight_id": "p1",
  "metric": "profit_margin",
  "question": "为什么利润率会失速？"
}
```

这就是为什么同一句话：

> “为什么？”

在不同页面里应该得到不同答案。

---

# 21. Tool Calling

Agent 不应该直接访问 PostgreSQL 的所有表。

应该通过工具：

```text
query_metric
query_orders
query_returns
query_products
query_stores
query_suppliers
query_evidence
create_watch
create_action
```

工具返回结构化结果。

例如：

```json
{
  "tool": "query_supplier_price",
  "arguments": {
    "supplier": "B",
    "days": 30
  },
  "result": [...]
}
```

---

# 22. Evidence First 原则

Agent 推理前先组证据。

推荐：

```text
Tool Result
    ↓
Evidence Record
    ↓
Evidence Bundle
    ↓
LLM Reasoning
```

而不是：

```text
LLM
 ↓
猜原因
 ↓
再找数据
```

这样可以显著降低幻觉风险。

---

# 23. Confidence 不能由 LLM 随便生成

Demo 里存在：

```text
置信度 86%
```

正式版本不要只是 prompt：

> “给我一个 86% 的置信度。”

应该由一个 Confidence Aggregator 计算。

输入可以包括：

```text
数据完整性
趋势稳定性
归因强度
证据覆盖度
规则命中强度
模型一致性
```

然后再形成：

```text
confidence_score
confidence_reasons
```

---

# 24. Action Execution

“立即执行”首先不要接真实生产系统。

第一阶段：

```text
创建执行任务
↓
模拟执行
↓
生成 execution record
↓
生成 result snapshot
↓
更新 action case
```

第二阶段再接：

```text
采购系统
CRM
ERP
IM
邮件
工单系统
```

这样 Demo 不会因为外部系统不可用而卡住。

---

# 25. Redis / 定时任务

Redis 用于：

```text
任务队列
缓存
SSE 状态
短期 Agent Context
```

定时任务负责：

```text
数据更新检查
Metric Recalculation
Watch Check
Signal Generation
Insight Refresh
Action Verification
```

推荐实现：

```text
Celery / Redis
```

# 26. 一次完整主动发现的后台流程

当 09:32 数据更新：

```text
1. Ingest
   ↓
2. Validate
   ↓
3. Normalize
   ↓
4. Metric Snapshot
   ↓
5. Rule Evaluation
   ↓
6. Generate Signals
   ↓
7. Group Signals
   ↓
8. Generate Insights
   ↓
9. Build Evidence
   ↓
10. Calculate Confidence
   ↓
11. Rank Insights
   ↓
12. Update Pulse
   ↓
13. Check Watch Targets
   ↓
14. Escalate if needed
   ↓
15. Push Event
```

这才是 Dora 的“主动性”。

# 27. Frontend 与 Backend 的边界

前端负责：

