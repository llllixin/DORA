## 2. V2 剩余内容（当前唯一"打开"版本）

按建议的 OpenSpec change 拆分（每项独立 propose → apply → archive）：

- [ ] **C1 · 引擎覆盖补齐**：把 c2（数据更新事件）、o2（华东门店集群）纳入规则覆盖，消除静态兜底；证据补全（退货 SKU/原因、新品门店共性、east 升级联动）
- [ ] **C2 · PostgreSQL Repository**：`engine/dataset.py` 换成数据库 Repository（指标/信号/洞察落表）；规则参数配置化（去掉写死的阈值）
- [ ] **C3 · 真实数据上传**：`POST /api/datasets` 解析 xlsx/csv 校验落库，成为引擎输入源（接 V1 冷启动入口）
- [ ] **C4 · 判断语义再收敛**：上传后"口径确认/字段映射"步骤（承接 Metric Definition 语义）
- [ ] **C5 · 质量护栏**：最小 E2E（文档 4 个核心验收用例：问题→Evidence→Action / 机会→复制验证→Action / 变化→Watch / Watch→升级→Problem）
- [ ] 收尾杂项：数据源名称下沉到页面文案；引擎结论与页面数字的一致性核对

> V2 完成判据 = C1–C5 全部归档 + 4 个 E2E 用例可自动跑通。

## 3. V3/V4/V5 的进入条件（防止提前做）

- **V3（LLM）** 只在 PostgreSQL 上的 Metric→Rule→Signal→Insight 链路跑通后启动（D009/D014）。
- **V4（Watch 调度）** 需要业务对象稳定 + V3 可用；引入 Redis/Celery。
- **V5（Action 闭环）** 需要 action_case/action_step 状态表 + 执行回写语义成熟。

## 4. 质量锚点（每个版本验收共用）

- 文档第 42 章检查清单：build 成功、FastAPI 启动、Pulse/Insight/Evidence/Action/Watch 全链路正常、无"页面写死业务判断"、API 边界清晰。
- 4 个核心 E2E 用例（第 36 章）可运行。
- 每个 OpenSpec change 归档 = 该范围内容已验收并有文档记录。

## 5. 更新约定（写代码的人必须遵守）

1. 完成任一迭代或 change → 刷新本文「版本速览 / 当前状态」。
2. 新增/关闭 OpenSpec change → 在 C1–C5 清单同步勾选并写 change 名。
3. 大版本切换（V2→V3 等）→ 在版本速览移动状态标记，并说明进入条件已满足。
