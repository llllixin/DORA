## 3A. V3 · Dora Reasoning —— 详细规划（Planning）

> 定位一句话：**让"判断"保持确定性（引擎不变），只把"解释文案"从模板换成 LLM 生成。**
> 原则（D009/D014 衍生）：数值/判定/触发条件永不来自 LLM；LLM 只能引用引擎给出的事实来组织语言。

### 3A.1 范围与非目标
**范围（In scope）**
- 解释/总结/建议文本的生成来源抽象为 `ReasoningProvider`（引擎模板作为默认 provider，行为不变）。
- LLM Provider（OpenAI 兼容 chat/completions）：输入=引擎上下文（trigger/factors/evidence 行/metrics/semantics 现状），输出=与现契约一致的文案（desc/question/causeA/causeB/next/reason 的**文本部分**）。
- 语义缓存：新增 `insight_reasoning` 持久化（insight_id→payload+provider+generated_at）；`/api/insights` 内联语义先取缓存，无缓存回退模板并标注 `reasonSource`。
- 手工"重新解释"入口（前端按钮 + `POST /api/reason/refresh`）。
- 质量与降级：无 key/网络失败 → 自动回退模板（页面可见 `AI 解释失败，已回退模板`），绝不阻塞引擎输出。

**非目标（Out of scope）**
- Agent 编排 / 工具调用 / 多步推理（不进 V3）。
- Dora Chat SSE 对话流（另立能力）。
- 自动建档 action case / Watch 动态委托（V4）。
- 修改任何判定逻辑、规则、evidence 原始行。

### 3A.3 接口信息（V3 新增，均向后兼容）
```text
POST /api/reason/refresh
  body:  { }                       # 空 = 对当前引擎全部洞察逐条生成
  resp:  { ok:true, updated:[ids], fallback:[ids], provider:"llm|template" }
  # fallback = 未配置 key 或 provider 出错被模板接管的洞察；重复调用幂等（有缓存直接返回）。

（展示层仍走既有 GET /api/insights / /api/insights/{id}）
  # 语义字段不变：semantics{causeA,causeB,next,desc…}
  # 新增只读标注：reasonSource:"llm"|"template", generatedAt?:ISO
```
```text
环境变量（backend/.env）：
  DORA_REASONING_PROVIDER=template|llm   # 默认 template（无 LLM 也可全绿）
  DORA_LLM_BASE_URL=https://api.openai.com/v1
  DORA_LLM_API_KEY=…                      # 未设置 → 自动 template 降级
  DORA_LLM_MODEL=gpt-4o-mini
```
错误语义：LLM 侧 401/429/5xx → 该洞察回退模板（返回含在 `fallback`），API 本身返回 200；引擎端点不受影响。

### 3A.4 最终验收与审查计划
1. **功能验收**：打开任意洞察详情 → 可点"AI 解释/重新解释"；来源徽标正确；无 key/断网时自动回退模板并提示；刷新后缓存复用。
2. **判定不被污染（关键红线）**：provider mock 输入同一 context 输出不同文案时，断言 metric/delta/trigger/evidence/置信度**逐字段不变**（LLM 只动文本）。
3. **金样本/回归**：`DORA_REASONING_PROVIDER=template` 时 `tests/run_all` 全绿且 `/api/insights` 与 V2 结果一致。
4. **接口审查**：新增端点契约写入 openspec（V3 各 change 的 spec delta）；README 需求来源表同步。
5. **审查人核对项**：本规划 §3A、各 change 的 proposal/spec/design/tasks、`docs/开发问题与经验.md` D022+；大版本切换：验收通过后把版本速览 V3 标为已完成（记录迭代）。

### 3A.5 进入 V4 的判据
V3 验收清单全过 + 业务对象稳定 + Watch/Action 静态域说明仍有效时，再开 V4 planning（不提前）。

## 3B. V4 · Watch 真实委托 —— 详细规划（Planning）

> 定位一句话：**把"持续关注"从静态列表升级为真实业务委托**：用户一句话托管目标 → 解析为 WatchTarget → 由引擎按频率评估 → 命中变化送回业务脉搏，跌破升级条件给出升级事件。
> 对应搭建文档第 12/33 章与 Case 3/4；V4 只做"委托 → 评估 → 事件 → 回脉搏"，**Action 闭环留给 V5**。

### 3B.1 范围与非目标
**In scope**
- 持久化：`watch_target`（原文 + 解析后的 metric_key/dimension/条件/频率/状态）+ `watch_event`（命中历史：时点/前后值/事件语义/是否升级）。
- 委托解析：中文语句 → WatchTarget 结构化字段；**规则词典 + 显式确认**（引擎支持的 metric key + 中文别名 + 区域名 + 条件句式）；无法映射 → 明确拒绝"暂不支持该指标"，不静默假设。
- 通用 Watch 评估器：从 `engine.py` 抽取可复用原语（`_streak_below` / `_breach` / `_below`），使"连续 N 天下跌 / 跌破 X% / 高于 X"可对任意受支持的 metric_key × dimension 求值（现 east 升级链路是特例，泛化为通用 watch 规则骨架）。
- 触发时机：① "数据更新时"——上传/样例成功后**即时**评估（与 `/datasets` 事务同链）；② "每日/每周 xx:xx"——进程内轻量调度线程 tick（**不引 Redis/Celery**，D009 维持）。
- 命中与升级：命中 → 写 `watch_event` + 回业务脉搏（Pulse「持续关注」真实化：最新事件/状态 Tag/升级提示）。升级**只以事件与标签呈现**；不伪造引擎未判定的 problem 身份。
- API：`/api/watch` CRUD + `/api/watch/parse` + `/api/watch/{id}/check`。
- Watch 页真实化：委托输入回显真实解析结果、目标列表/状态/频率来自后端、支持暂停/删除/手动检查。

**Out of scope**
- Action 闭环（Case/Step/Execute/Result/Verify/Resolve）→ V5。
- LLM 意图解析：判定不进 LLM（红线延续）；未来 LLM 只可给"候选"，必须规则收敛 + 用户确认。
- Redis/Celery 分布式调度、SSE 实时推送、Dora Chat 追问（仍另立，见 §3A 非目标）。
- 不受引擎支持的指标/映射不明确的"假装关注"（宁可拒绝，不造假）。

### 3B.3 接口信息（V4 新增；GET /api/pulse 扩展而非破坏）
```text
POST /api/watch/parse      { text } → { ok, intent?:{metric_key,dimension,condition:{type,days,ref},frequency}, unsupported?:[...] }
POST /api/watch            { text, frequency } → { ok, target:{id, parsed, status:"watching"} }   # 创建即首次评估（幂等：同 text 去重）
GET  /api/watch            → { ok, targets:[{id, name, status, frequency, logic, value, last_event_at?, escalated?}] }
GET  /api/watch/{id}       → target + events[]（时点/前后值/语义/是否升级）
PATCH /api/watch/{id}      { status:"paused"|"watching" }
DELETE /api/watch/{id}     # 同时清其事件
POST /api/watch/{id}/check → 手动立即评估（验收/测试用）
# GET /api/pulse 持续关注区：从 watch_targets 实时 + watch_events 最近命中聚合
```
频率枚举：`on_update`（数据更新时，默认）/ `daily 09:00` / `weekly`。升级语义：复用引擎阈值风格（如 `_breach`）；**升级事件 ≠ problem 身份**，是否成为正式问题仍由引擎在数据满足既有 rule 时判定（V5 把 case 接上）。

### 3B.4 红线与验收计划
1. **判定不造假**：Watch 的所有 value/前后值/命中结论来自 Repository 序列与引擎原语；watch 命中只产生 watch_event + Pulse 呈现，不伪造引擎未判定的 problem/opportunity（参考 V3 数值锁 D 系列）。
2. **支持范围显式**：只有引擎 `METRIC_SERIES_KEYS` + 已知区域/条件可建 watch；unsupported 一律拒绝并给候选，绝不静默兜底成"关注任何变化"。
3. **降级诚实**：DB down → /api/watch 系列 503（与上传一致，不回退 Mock 数据）；前端离线才走 data.ts 兜底并标注。
4. **回归锚点**：golden 9 insights 模板基线不变；e2e Case 1/2 不受影响；Case 3/4 由新 watch_check 覆盖。
5. **spec/导航**：V4 归档新建/更新能力 spec `business-watch`；README 需求来源表 + 索引同步（沿用 V3-T5 做法）。
6. **审查人核对**：本规划 §3B、各 change proposal/spec/design/tasks、P/D 记录 D029 起；验收通过后版本速览 V4 标完成。
